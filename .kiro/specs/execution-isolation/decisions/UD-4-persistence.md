## Alternatives and smallest proposal
| Option | Benefit | Limitation |
|---|---|---|
| Local SQLite + immutable scoped artifact storage | Offline, small operational surface, one metadata transaction | Storage/VFS durability must be qualified; no intrinsic project authorization or authenticated history. |
| Remote PostgreSQL | Central transaction ordering for multiple coordinators | Network/credential/outage/operations surface; cannot serve a strict offline request remotely. |
| Object storage alone | Immutable copies and backups | Strong consistency does not supply a multi-key state/audit/budget transaction. |
| Custom append log | Offline | Bespoke torn-write recovery, conditional ordering, indexing and restore add correctness burden. |

Recommendation (inference, not selection): evaluate one trusted coordinator and one local SQLite metadata database with separately scoped immutable artifacts. Start by comparing rollback journal with `synchronous=EXTRA`; do not add distributed coordination or WAL until a demonstrated requirement warrants it. Exact SQLite version, Rust binding/dependency/license, filesystem/VFS and journal configuration remain unselected.

Context7 resolve/query of SQLite plus official docs reviewed 2026-10-22: synchronization guarantees depend on journal mode and storage behavior; WAL adds same-host/network-filesystem and backup/checkpoint considerations. Current WAL docs flag a version-specific reset corruption fix: any selected engine must be verified against current advisories, not inferred from a wrapper name. [Synchronization](https://www.sqlite.org/pragma.html#pragma_synchronous), [WAL](https://www.sqlite.org/wal.html). PostgreSQL asynchronous commit may lose acknowledged transactions on crash. [PostgreSQL](https://www.postgresql.org/docs/current/wal-async-commit.html). S3 lacks atomic cross-key updates. [S3 consistency](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel).

## Proposed authoritative ordering
These are backend-independent review rules, not a selected schema or implemented transaction protocol.

| Boundary | Proposed durable rule / resulting authority |
|---|---|
| Identity and ordering | Trusted coordinator binds `(tenant, project, run, attempt, transition-id)` plus operation digest and expected state/version. A successful conditional transition increments the authoritative per-attempt version; cancellation/revocation/exhaustion and acceptance compete in this same order. Wall timestamps are descriptive, not the tie-breaker. Same ID/different digest is rejected; stale versions require readback, not overwrite. |
| CP-0 / CP-1 | Admission state, attributable audit, cumulative run-budget reservation and checkpoint commit atomically before dispatch. Persist dispatch intent before allocation, credential use or launch. An intent is not evidence that an effect happened. |
| CP-2 / CP-3 | Freeze scoped artifacts and verify their digests/durability before committing references. Commit state/version, linked audit event, observed budget disposition and checkpoint as one unit. Require current policy and confirmed relevant cleanup; staged/orphan bytes never imply completed verification or acceptance. |
| CP-4 acceptance | Recheck current scope, policy/retention, fresh bound approval, complete same-binding evidence, budget and cleanup inside the authoritative ordering boundary. State `accepted`, its audit link, final budget disposition and CP-4 become visible atomically, or none do. No partial record is an acceptance receipt. |
| Cancellation / revocation / exhaustion | If ordered first, commit `stopping` and prohibit acceptance/dispatch; reconcile effects, revoke and clean up before a terminal `cancelled`/`blocked` disposition. If CP-4 committed first, read back `accepted`; never reopen or relabel that terminal attempt. Withdrawal still removes future authority and affected live-content access. |
| Lost acknowledgement / partial writes | Outcome is unknown until the same transition ID, digest, version and complete linked record are reconciled. One complete committed transition is read back once; absent/uncommitted work conveys no success. Contradictory partial records, unknown effects/accounting or missing blobs block recovery; do not blind-append, re-dispatch or release/reset reservations. |
| Outage / trusted head | Required-store failure denies dispatch and acceptance, never emergency containment, revocation or termination. Recovery records only observable gaps. A hash chain alone cannot establish freshness: restore requires an independently trusted authenticated head/checkpoint and current deletion-state authority, available without run-serving outbound traffic in offline mode. Missing head blocks recovery/acceptance; do not claim rollback protection from an old valid prefix. Mechanism and coverage remain MISSING. |

Every read/write/list/cache/export/delete/restore rechecks trusted tenant **and project** authorization, current policy and deletion state. Equal hashes, database file permissions, a historical approval or a parsed declaration grant no authority. Terminal outcomes remain immutable; retries require a separately authorized attempt within remaining cumulative budget and fresh verification/credential authorization.

## Retention decision table — concrete PROPOSED values, APPROVAL MISSING

All numbers below are **DRAFT owner-review proposals**, not legal/compliance defaults, approved retention policy, production configuration or measured UD-5 runtime budgets. No production activation follows from this document. A policy revision and named operations/security approvals for every applicable class are required before persistence or dependent launch; otherwise `[RETENTION_UNCONFIGURED]`. Do not implement a custom retention engine from this table.

**Clock convention:** `created` is first trusted ingestion/creation, `terminal` is the originating run's terminal transition, `last use` is an authorized use. At creation assign the absolute cap; reaching it expires content even if the run is nonterminal (dependent work then blocks). Expiry `E` is the earliest applicable row deadline, current-policy narrowing, project deletion or approval-withdrawal restriction. Access ceases at `E`; erase managed active bytes by `E + 24 hours` and record failure explicitly. Copies, access, retries, exports and restores never restart the original class clock or extend its cap. Backup rules below bound residual copies separately.

Responsibilities are proposed functions, **not named/approved owners**: **P** = trusted project-storage owner (scope, deletion/tombstone); **C** = coordinator/audit owner (state, metadata and verification availability); **O** = operations backup owner (copy inventory, expiry, quarantine and restore checks); **X** = export authorizer (recipient terms and receipts). Operations/security must approve the policy; only authenticated authorized deletion actors or approved expiry policy may request deletion. Workers cannot author trusted deletion/audit records.

### Withdrawal, deletion, holds and restore review rules

- **Approval withdrawal:** immediately revoke future operation/acceptance authority and affected content access; stop affected active work without waiting for audit availability. As proposed, affected content enters expiry/purge at withdrawal under the E + 24-hour rule; minimal scoped audit/deletion metadata follows its separate row. An already accepted attempt remains historically accepted, not usable as new authorization. Project deletion invalidates all project-content access immediately, including cache/index/export links; only explicitly authorized deletion/retention administration can see minimal retained metadata.
- **Maximum retention and holds:** no longest-row-wins policy. Derived data uses its own deadline **and** source restrictions; source deletion invalidates derived access. A hold is possible only through a separately approved, explicitly authorized control naming scope/classes, reason, approver, finite expiry and restricted custodians, with a recorded superseding deletion schedule. A hold grants no worker/application access and is not created by this draft, a backup, an active run or missing policy. Hold support/approval is MISSING; do not silently extend retention.
- **Retained copies:** immediate logical invalidation is not physical erasure. A deleted object in an older backup remains restricted until at most snapshot + 35 days; receipts report class, copy inventory, expiry and physical-erasure limitations, including storage remnants and external recipients. A missed purge deadline is a failure/incident, not permission to retain indefinitely or claim erasure.
- **Restore:** restore only into inaccessible quarantine. Apply an independently current deletion ledger and policy revision, original class clocks, scope and authenticated-head checks **before** any exposure. Never replace that ledger with the snapshot's historical ledger. The proposed 180-day ledger window exceeds the 35-day operator-backup window; after ledger expiry, unknown or out-of-window snapshots remain denied, not assumed undeleted. Restores missing current restrictions stay inaccessible and expire under quarantine limits. No resurrection of previously deleted bytes or acceptance based on expired evidence.

Use a consistent approved backup mechanism, not an unqualified copy of live database files. SQLite `secure_delete` is not whole-system/backup erasure evidence. [Backup API](https://www.sqlite.org/backup.html), [secure deletion limits](https://www.sqlite.org/pragma.html#pragma_secure_delete).
